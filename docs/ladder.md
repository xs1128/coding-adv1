# Optimization ladder

Every experiment we ran, oldest first. Each kept change is the starting point for the next, like rungs of a ladder.

- **Start**: `results/base/official_1g` (job 600407): MFC v5.7.0, NVHPC 26.3, 1 H200 GPU, grind 0.3982 ns, step 77.06 ms.
- **step / ms**: median time of one simulation step. **grind**: MFC's speed number (ns per grid point per
  equation per pass). Lower is better. **wall**: the whole run. **4g**: 4 GPUs; **rdma**: GPUs send data
  straight to each other.
- **A/B**: old (A) and new (B) builds timed in the same job, so only the change differs; "×2" means two rounds.
  **bitwise ✓**: the answer matches the old one in every bit, so the physics did not change.
- **kernel**: one GPU function run over many cells. **WENO5** builds smooth values at cell faces; **HLLC** (a
  Riemann solver) works out what flows between two cells; the **RK update** moves the solution one sub-step
  (stage) forward. **Fused**: merged into one kernel. **Unity file**: several source files compiled as one.
- **Registers**: each GPU thread's tiny fast storage. Capping them lets more threads run at once (warps or blocks
  per SM, an SM being one of the GPU's processor blocks), but extra values **spill** to slow memory (the
  stack). LDG/LDL/STL count kinds of memory loads and stores in the GPU machine code.
- **Kept?** yes = it goes into the code; rejected rows stay listed. **P…** are kept patches (`patches/opt/`); **exp-…** are side experiments (`patches/exp/`).

### Why HLLC was slow (K4): 1.88–2.19 ms per call vs 1.46 in v4.9.3
- ncu (job 600146): 18.75 % occupancy (160 registers). **More traffic to local memory (each thread's private
  overflow space) than to global memory**; DRAM writes 2.1 GB vs 1.1 GB read.
- Cause: nvfortran does not paste (inline) small helpers from other source files into GPU code (#2094). The kernel
  makes 9 real function calls whose arguments live in local memory, and it reloads values after every store
  (`m_riemann_solver_hllc.fpp:1208`).
- Helpers in the same file do get inlined. Compiling the HLLC file with the helper modules as one unit gives 150
  registers, LDL 76 / STL 8. → K4b (row 4).

### Why the fused RK update is still ~2× off bandwidth (ncu job 681191, exp-bcfast)
- `results/prof/ncu_bcfast_rk/ncu_details.csv`: 1.50 ms, DRAM 46.7 % (2.25 TB/s), SM 29.2 %, 148 registers,
  theoretical occupancy 18.8 % (3 warps per scheduler), achieved 17.9 %. Each warp waits on loads most of the time.
- So it is latency-bound: too few warps in flight to cover memory delay. The obvious fix (fewer registers, more
  warps) was already tried in row 45 and lost (spills cost more than the extra warps help), and the one-thread-per-
  equation split (row 38) redoes shared work. No cheap win left here; the next idea would be explicit prefetch
  through shared memory, which OpenACC/OpenMP macros cannot express portably.

### Where a stage goes after 0027 (nsys job 683428, exp-cbcdead, 1 GPU, 10 steps)
- `results/prof/nsys_cbcdead_1g`: per RK stage the fused WENO5+HLLC sweeps take 2.23 / 2.32 / 2.32 ms (x / y / z, 70 %
  of kernel time), the fused RK update 1.50 ms (15 %), the conversion to primitives 0.50 ms (5 %); everything else is a
  few percent. The GPU is idle only ~0.02 ms per stage. Only the HLLC sweeps are big enough to matter now.
- ncu of the fused kernel (`results/prof/ncu_fslab_fused`): 128 registers (the cap), 25 % occupancy, local-memory
  traffic 26 % of all memory traffic. Raising the cap was last tried on P13 (row 17), before fusion and the slabs.

### What is left of a 1-GPU run with `ob1` and `/dev/shm` (nsys 684808, CPU sampling + OS runtime)
- The simulation process takes ~2.87 s: MPI start-up 0.66 s (mostly the CUDA driver setting up: 207 ms of `ioctl`),
  reading modules and the initial state 0.55 s (115 ms of `pread` from RAM plus a CPU copy into the arrays), GPU set-up
  0.07 s, time loop 0.89 s, save 0.48 s (the 311 ms pageable device-to-host copy plus 180 ms of `pwrite`), finish 0.07 s.
- The one sizeable piece left is that copy. Fixing it needs pinned host buffers, which OpenACC/OpenMP cannot allocate
  portably; the runtime's own pinning settings were slower (row 54). Stopped here.

### What the fused kernel's local-memory traffic is (machine code of exp-cbcdead, no GPU run)
- `cuobjdump -sass` of the x-sweep kernel: 257 local loads (210 of them 64-bit) and 52 local stores against 158 global
  loads; 86 `CALL`s. The relocation table names the calls: 71 × `__cuda_sm20_dblrcp_rn_slowpath_v3` and 13 ×
  `__cuda_sm20_dsqrt_rn_f64_mediumpath_v1`, the correctly rounded FP64 division and square-root fallbacks, taken only for
  rare inputs (subnormals and the like). They are what keeps results bitwise and cannot go.
- So the local traffic is register spilling under the 128-register cap; caps 64–255 were all measured (rows 6, 17, 24, 42,
  51) and 128 is best.

### Why the ranks wait at 4 GPUs, and the next idea (nsys 685113, no new GPU run)
- 4 ranks split the grid 2 × 2 (x and y). Per step, ranks spend the same time in every kernel except CBC: 0.16 / 0.36 /
  0.40 / 0.59 ms on ranks 0–3, because each rank runs CBC only on the domain-end faces it owns (rank 3 owns x, y and z).
  The busiest rank idles 0.56 ms per step and its swaps take 54 µs; rank 0 idles 1.17 ms and its swaps take 175 µs.
  So the halo-exchange "wait" is mostly ranks waiting for rank 3's CBC work.
- The CBC FD kernel (`s_cbc_618`) takes 28–39 µs per face with only 79–316 blocks, so the GPU is mostly idle while it runs.
  At 1 GPU the whole CBC path is 389 µs per stage (`nsys_cbcdead_1g`), about 4 % of a step.
- Next idea, not built: since 0027, CBC reads only the primitive state (ready before the sweeps), so its setup,
  conversion and FD kernels could run on a second OpenACC queue alongside the HLLC sweeps, with only the copy-back kept
  after HLLC on the main queue. That needs the CBC module's per-call settings (direction, side, index ranges) kept per
  direction instead of in shared module variables, and must keep the original order when both sides of a direction are
  CBC. Expected: about 1–2 % at 1 GPU, more at 4 GPUs, where it would also even out the ranks.
- The CBC FD kernel itself (`s_cbc_651` after 0028; machine code, no GPU run): 114 registers and a 448-byte stack per
  thread (its small per-point arrays live in local memory). Its ~316 blocks all fit at once, so its 39 µs is one thread's
  chain of dependent steps. Shortening it would mean making those arrays register-resident (full unrolling), a deeper
  rewrite; with 0028 hiding most of it behind HLLC, at most about 1 % is left there.

### What is left at 1 GPU after 0029 (nsys 685403, no new GPU run)
- Outside the three big kernels, about 1.2 ms of small-kernel time per step is not overlapped: the ghost-cell fills
  (~0.6 ms), the CBC copy-in/copy-back kernels (~0.38 ms), and 147 tiny host-to-device copies (0.14 ms of GPU time,
  ~0.4 ms of CPU time). Another 0.56 ms per step the GPU sits idle.
- That idle time follows one host wait per RK stage (`cuStreamSynchronize`, 11 ms per step in total): the synchronous
  `GPU_UPDATE(device='[mytime]')` right before MFC's own per-stage timer (`system_clock`), which is what the grind time is
  measured from. Letting the host run ahead would change what that timer measures, so it stays.
- The 9 `cuEventSynchronize` per step (15.9 ms of host waiting) come from 0028's "default queue waits for the CBC
  queue": NVHPC implements that wait on the host. The Riemann solve is still running then, so the GPU does not starve.

### Offline review of 0030 (no GPU time; nano4 login lapsed)
Applied 0001–0030 to a local v5.7.0 copy and read the result:
- The early `return` skips nothing else: the per-cell loop is the last statement of `s_populate_bc_direction`, and its

  it from patches too, and the shared code has no per-program macro), so it stays a follow-up to measure first (nsys host
